# 回滚与重建流程

> 基于 `reconstruction.ts`、`session-coordinator.ts`、`context-manager.ts` 源码整理

---

## 整体数据流

```
磁盘日志 (.jsonl)
    │
    ▼ readRollout
原始 TranscriptEnvelope[]
    │
    ▼ applyRollbacks（阶段二）
surviving TranscriptEnvelope[]
    │
    ▼ 找 last checkpoint + 增量回放（阶段三）
ReconstructedSession
    │
    ▼ context.restore（阶段四）
内存 ContextManager
    │
    ▼
后续 turn 在回滚点基础上继续运行
```

---

## 核心前提：Transcript 统一日志模型

Transcript 不是"事件列表"，而是统一追加日志。所有类型的记录都混在同一张日志里，靠 `kind` 字段区分：

| kind | 说明 |
|------|------|
| `session_meta` | 会话元信息 |
| `turn_started` / `turn_completed` / `turn_aborted` | turn 生命周期 |
| `message` | 对话消息 |
| `tool_call` / `tool_result` / `tool_preview` | 工具调用链 |
| `approval_requested` / `approval_resolved` | 审批流程 |
| `compact_checkpoint` | 压缩快照 |
| `world_state` | 世界状态 |
| `reference_context` | 参考上下文 |
| `rollback` | 回滚标记 |
| `interruption_marker` | 中断标记 |
| `fork_created` | 分叉标记 |

每条记录都是 `TranscriptEnvelope`，结构相同（ordinal、timestamp、kind、payload），只是 kind 不同、payload 类型不同。

## 阶段一：编排层

**代码位置**：`session-coordinator.ts:245-269`

**职责**：校验边界 → 追加回滚记录 → 触发重建 → 恢复内存

**执行步骤**：

1. **flush()** — 确保所有待写日志落盘
2. **readRollout()** — 读取当前完整日志
3. **边界校验** — throughOrdinal 对应的记录必须存在，且 kind 必须是合法回滚边界：
   - 合法边界 kind：`session_meta`、`turn_completed`、`turn_aborted`、`compact_checkpoint`、`world_state`、`reference_context`
   - 不合法则抛异常，拒绝回滚
4. **persist("rollback", { throughOrdinal })** — 向日志追加一条 `kind="rollback"` 的记录
5. **flush()** — 再次落盘（rollback 记录本身也必须持久化）
6. **readRollout()** — 重新读取（此时包含刚写入的 rollback 记录）
7. **reconstructSession(records)** — 进入阶段二 + 阶段三
8. **context.restore(state)** — 进入阶段四

**关键设计**：rollback 不是直接删除文件中的记录，而是追加一条 `kind="rollback"` 的标记。真正的裁剪在重建时逻辑执行。

## 阶段二：日志裁剪层

**代码位置**：`reconstruction.ts:108-121`

**职责**：从日志流中逻辑删除被回滚的记录

**算法**：

```
surviving = []
for record in records:
    if record.kind != "rollback":
        surviving.push(record)
    else:
        through = record.payload.throughOrdinal
        while surviving 末尾 ordinal > through:
            surviving.pop()
        surviving.push(record)    // rollback 记录自身保留
return surviving
```

**算法特征**：

- 单次顺序扫描，O(n)
- 从 surviving 数组尾部 pop，保证只删 ordinal > through 的记录
- rollback 记录自身保留在 surviving 中（作为历史标记）
- 如果 through 指向未来（through ≥ record.ordinal），直接抛异常

**重要说明**：surviving 数组存放的不是"纯事件"，而是经过回滚裁剪后的全量 Transcript 记录流，包含所有 kind（message、tool_call、compact_checkpoint、world_state 等）。

## 阶段三：状态重建层

**代码位置**：`reconstruction.ts:46-106`

**职责**：从 surviving 日志还原内存会话状态

### 3.1 确定 base

从 surviving 中过滤出所有 `kind === "compact_checkpoint"` 的记录，取最后一个作为 base：

- 有 checkpoint → `baseOrdinal = checkpoint.ordinal`，`annotatedHistory = checkpoint.replacementHistory`（快照）
- 无 checkpoint → `baseOrdinal = -1`，`annotatedHistory = []`（空数组）

无 checkpoint 不是特殊分支，只是 `?? -1` 和 `?? []` 的自然兜底，与正常启动无 checkpoint 时的行为完全一致。

### 3.2 增量回放

遍历 surviving 中的每条记录：

- **始终执行**：`trackRecovery()` — 追踪 turn 生命周期、审批状态、工具调用状态（用于恢复 incompleteTurnIds、pendingApprovalRequestIds、unknownOutcomes）
- **baseOrdinal 跳过**：`ordinal ≤ baseOrdinal` 的记录跳过（checkpoint 的 replacementHistory 已包含这些内容）
- **按 kind 处理**：
  - `message` → 追加到 annotatedHistory
  - `world_state` → 通过 `applyWorldState()` 累积更新
  - `reference_context` → 根据 `cleared` 字段决定是否保留
  - 其他 kind → 不直接拼 history，由 trackRecovery 处理

### 3.3 组装结果

返回 `ReconstructedSession` 对象，包含：

| 字段 | 来源 |
|------|------|
| `history` | annotatedHistory 中提取 message |
| `annotatedHistory` | 快照 + 增量回放后的完整列表 |
| `historyVersion` | surviving 中 message + compact_checkpoint 记录数 |
| `window` | checkpoint.window 或 session_meta 初始值 |
| `referenceContext` | 增量回放中最后一个 reference_context |
| `worldStateBaseline` | 增量回放中累积的 world_state |
| `latestCheckpointOrdinal` | 最后一个 checkpoint 的 ordinal |
| `incompleteTurnIds` | trackRecovery 追踪的未关闭 turn |
| `pendingApprovalRequestIds` | trackRecovery 追踪的待审批 |
| `unknownOutcomes` | trackRecovery 追踪的结果未知工具调用 |
| `lastOrdinal` | 原始记录的最后 ordinal |

## 阶段四：内存恢复层

**代码位置**：`context-manager.ts:88-95`

**职责**：用重建结果替换内存中的所有上下文状态

**还原字段**：

| 字段 | 含义 |
|------|------|
| `items` | 对话历史（annotatedHistory） |
| `window` | 上下文窗口（ContextWindowState） |
| `reference` | 参考上下文 |
| `world` | 世界状态 |
| `checkpointOrdinal` | 最近 checkpoint 序号 |
| `version` | 版本号递增 |

**一致性保证**：一次性替换所有字段，保证 items/window/reference/world/checkpointOrdinal 五个维度在同一回滚点上对齐。不采用逐字段渐进更新，避免中间态不一致。

## 场景对照

### 场景 A：正常运行，有压缩快照

```
日志：[meta, msg1-50, checkpoint, msg51-80]
回滚 throughOrdinal = 60

applyRollbacks → surviving = [meta, msg1-50, checkpoint, msg51-60]
重建：baseOrdinal = checkpoint.ordinal
  → annotatedHistory = checkpoint.replacementHistory + msg51-60
  → 50 条原始记录被快照替代，只回放 10 条增量
```

### 场景 B：回滚删掉了所有 checkpoint

```
日志：[meta, msg1-10, checkpoint, msg11-30]
回滚 throughOrdinal = 10

applyRollbacks → surviving = [meta, msg1-10]
重建：baseOrdinal = -1（无 checkpoint）
  → annotatedHistory = [] + msg1-10 全部回放
  → 等价于从头重建，无特殊分支
```

### 场景 C：正常启动，从未压缩

```
日志：[meta, msg1-20]
无 rollback

applyRollbacks → surviving = [meta, msg1-20]（无变化）
重建：baseOrdinal = -1（无 checkpoint）
  → annotatedHistory = [] + msg1-20 全部回放
  → 与场景 B 的代码路径完全相同
```

## 修正对照表

| 之前的描述 | 修正后 |
|-----------|--------|
| 阶段三叫"跨 checkpoint 回退处理" | 不存在独立阶段，是重建阶段的自然兜底 |
| checkpoint 被删是特殊处理 | `?? -1` / `?? []` 兜底，无特殊分支 |
| 混淆了回滚和重建的边界 | 阶段二 = 日志裁剪，阶段三 = 状态重建，职责分明 |
| rollback 是物理删除文件记录 | rollback 是追加标记，裁剪在重建时逻辑执行 |
| surviving 数组只存"事件" | surviving 存所有 kind 的 Transcript 记录 |
