# Phase 1 学习笔记

## 一、Phase 1 的定位

Phase 1 解决的是 Agent 的控制地基，不负责增强模型智力，而是把模型、工具、状态、配置和项目规则组织成一条可控制、可恢复、可扩展的运行链路。

这一阶段有两条主线。

- 执行控制：双层 Agent 循环、模型流式输出、事件流、输出解析、工具执行、并发安全。
- 运行上下文：分层配置、Prompt 组装、上下文预算、`AGENTS.md` 与 `CLAUDE.md` 注入。

完整数据流如下。

```text
启动入口
  -> 合并配置
  -> 注册工具
  -> 加载项目规则
  -> 创建 AgentContext
  -> 创建 AgentSession
  -> 规划并调度任务
  -> 构建 Prompt
  -> 请求模型流
  -> 聚合模型文本
  -> 解析 AgentAction
  -> 执行工具或结束任务
  -> 写入历史与轨迹
  -> 推进下一轮
```

掌握这一阶段的标准是能够说明每个状态由谁维护、循环为什么继续、数据在哪一层转换、错误在哪一层恢复、配置为什么得到最终值。

## 二、核心对象与职责边界

### 1. `AgentContext`

`AgentContext` 是一次 Agent 运行所需依赖的集合，包含配置、工具注册表、终端会话、模型客户端、工作目录和工作记忆。

核心原理是依赖显式传递。业务逻辑不从全局位置临时读取依赖，而是通过上下文获得稳定的运行环境。

优点：

- 依赖关系清楚，组件更容易替换和测试。
- 同一套循环可以接入不同模型、工具和工作目录。
- 运行期共享状态集中，减少隐式耦合。

缺点：

- 字段持续增加后容易变成通用容器，职责边界会减弱。
- 可变字段被多个工具同时读写时需要并发控制。

实现要点：

- 稳定依赖使用只读引用，避免运行中被替换。
- 可变状态单独建模，不与配置对象混在一起。
- 工具只通过 `AgentContext` 访问工作目录和运行资源。

当前 `workingMemory` 是普通对象，只适合保存少量会话提示。它没有版本、作用域和同步机制，不能承担持久记忆或正式任务状态。

### 2. `AgentSession`

`AgentSession` 是会话生命周期控制器，负责跨轮状态和终止条件。

它维护以下内容：

- 子任务调度状态。
- 消息历史 `history`。
- 执行轨迹 `trace`。
- 已完成任务摘要 `completedTasks`。
- 工具步数预算 `steps`。
- 事件分发。

`AgentSession` 不处理单轮内部的解析和工具执行细节，这些逻辑交给 `runTurn`。外层只根据单轮结果决定继续当前任务、切换任务或结束会话。

### 3. `runTurn`

`runTurn` 是单轮状态推进器，负责一次生成、解析、恢复和执行。

```ts
async function runTurn(options: TurnOptions): Promise<TurnResult>
```

输入包括历史、模型生成函数、解析器、工具名称集合、执行器、上下文和重试策略。输出包括动作、原始模型文本、工具观察结果或终止信息。

职责边界：

- `AgentSession` 决定是否还有下一轮。
- `runTurn` 决定本轮产生什么结果。
- `OutputParser` 决定模型文本能否转换成合法动作。
- `Executor` 决定动作如何调用工具并归一化错误。

这个拆分为上下文压缩、权限判断、传输降级和输出上限恢复提供了稳定插入点。

## 三、双层 Agent 循环

### 1. 双层结构的必要性

单层循环同时处理模型调用、解析重试、工具执行、任务切换、预算控制和最终结果时，任何局部跳转都可能遗漏其他状态更新。

双层循环把状态分成两类。

- 会话层状态：任务队列、总预算、完整历史、最终答案、跨轮恢复策略。
- 单轮状态：本次模型输出、本次解析结果、本次工具动作、本次观察结果。

适用场景：

- 一次任务需要多轮工具调用。
- 模型输出可能解析失败并需要重试。
- 后续需要加入压缩、审批、模型降级或中断恢复。
- 运行过程需要转换成事件供 CLI 或界面消费。

优点：

- 每层终止条件清楚。
- 单轮逻辑可以独立测试。
- 恢复策略可以按失败层次接入。
- 局部重试不会重新初始化会话状态。

缺点：

- 历史、轨迹和任务状态存在多个更新时机，需要规定唯一维护者。
- 单轮结果类型过于简单时，外层仍会依赖内部细节。

### 2. 外层循环

`AgentSession.run` 的推进顺序如下。

```text
规划任务
  -> 压入调度器
  -> 取出当前任务
  -> 构建本轮消息
  -> 执行 runTurn
  -> 处理解析失败
  -> 处理最终答案
  -> 记录工具步骤
  -> 进入下一轮
```

任务调度器使用栈。任务数组按逆序压栈，再从栈顶取出，因此实际执行顺序与规划结果一致。

当前 `steps` 只在工具调用完成后增加，最终答案和解析重试不计数。因此 `maxSteps` 实际限制的是工具执行次数，不是模型请求次数，也不是完整轮次数。预算名称必须与计数语义一致。

### 3. 内层循环

当前 `runTurn` 先消费完整模型流，再解析动作。

```text
stream_start
  -> 累积 text_delta
  -> 收到 done
  -> 解析输出
  -> 失败时写入修复提示并重新生成
  -> 得到 final_answer 或 tool_call
  -> 执行工具
  -> 写入 tool 消息
```

解析重试发生在同一轮内部。失败输出和修复提示会进入历史，使模型看到上一次违反协议的内容和修复要求。

优点是修复上下文完整。缺点是无效输出会占用上下文，并可能持续影响后续判断。后续压缩应优先删除解析失败产生的控制消息。

### 4. 继续原因与恢复站点

`ContinueReason` 定义了多类继续原因，但当前只有普通推进和解析重试形成真实行为，类型本身尚未驱动循环状态机。

各继续原因对应不同恢复语义。

- `normal`：保留本轮结果，正常进入下一轮。
- `parse_retry`：保留失败文本和修复提示，重新请求模型。
- `max_output_tokens_upgrade`：提高输出上限后重试，不能重复执行工具。
- `context_compacted`：压缩历史后重新构建 Prompt。
- `transport_fallback`：切换传输方式，不把网络错误当成推理错误。
- `tool_error_recoverable`：把错误观察结果交给模型决定修复动作。
- `auto_compact_failed`：停止自动压缩，避免无限恢复。

继续原因的价值是把分散的控制跳转提升为显式状态。单轮结果应携带结构化原因，外层再决定恢复策略。

## 四、消息历史、执行轨迹与事件流

三者都记录运行过程，但用途不同，不能混用。

### 1. 消息历史 `history`

消息历史是下一次模型推理的输入，属于模型上下文。

它包含用户任务、模型原始输出、工具观察结果和解析修复提示。

关键要求是保持对话结构完整。工具观察结果必须跟在产生工具调用的 assistant 消息后面，截断历史时不能留下孤立的 tool 消息。

### 2. 执行轨迹 `trace`

执行轨迹是程序侧审计数据，不直接进入模型上下文。

它保存结构化动作、观察结果、原始输出、步骤索引和时间戳，适合调试、回放、测试和后续可观测性。

两者的区别：

- 历史服务模型决策，需要控制 token。
- 轨迹服务程序分析，应尽量完整。
- 历史可以压缩，轨迹不应因上下文预算被删除。

### 3. 事件流 `AgentEvent`

事件流把内部执行过程转换成外部消费者可观察的增量信息。

当前终端消费了流开始、文本增量、工具开始和工具完成事件。事件类型还预留了 assistant 消息、API 错误、压缩边界、最终答案和最大轮数。

事件流的核心不是打印日志，而是解耦运行逻辑和展示逻辑。

优点：

- CLI、图形界面和日志系统可以复用同一运行核心。
- 消费者可以实时展示模型输出和工具状态。
- 运行核心不依赖终端输出函数。

缺点：

- 事件顺序会成为对外协议，变更需要兼容。
- 同步回调执行过慢会阻塞主流程。
- 事件丢失、重复或乱序会破坏界面状态。

实现要点：

- 每个工具调用使用独立 `callId`，不能用工具名代替调用标识。
- 事件负载保留必要结构，不只保留展示文本。
- 外部回调异常不能破坏 Agent 主循环。
- 事件历史需要设置上限，避免长会话持续占用内存。

当前实现把所有事件保存在私有数组中，但没有读取接口，形成无收益的内存增长。应当暴露事件快照，或者只向外分发而不长期保存。

## 五、模型流式输出

### 1. 流式接口

模型流式输出把一次完整响应拆成按时间到达的事件序列。

```ts
stream(messages, options): AsyncGenerator<ModelStreamEvent>
```

`AsyncGenerator` 同时提供异步等待和逐项消费。消费者通过 `for await` 读取增量，生成器通过 `yield` 交付事件，通过正常返回或抛错表示结束状态。

适用场景：

- 模型输出需要实时展示。
- 输出较长，不希望等待完整响应后再处理。
- 协议能在流中识别完整工具调用并提前执行。

优点：

- 降低首段结果的等待时间。
- 增量处理减少完整响应的临时内存压力。
- 为工具预执行和实时取消提供基础。

缺点：

- 网络分块、协议事件和业务事件的边界不同。
- 异常可能在迭代过程中发生。
- 提前退出时必须释放 reader、计时器和请求资源。

### 2. 当前能力边界

当前 `ModelStreamEvent` 只有 `text_delta` 和 `done`。`runTurn` 会把所有文本累积到 `full`，结束后才调用 `OutputParser`。

因此当前实现的是流式展示，不是流式工具预执行。

项目虽然创建了 `StreamingToolExecutor`，但没有把它传入 `runTurn`，也没有调用 `addTool` 或 `collect`。模型事件中也没有结构化 `tool_call`。这部分属于预留结构，不属于已生效能力。

真正的工具预执行需要同时满足：

- 传输层能产出结构化工具调用增量。
- 流式解析器能判断参数已经闭合。
- 已闭合调用立即进入执行队列。
- 流结束后统一收集结果并按调用顺序写入历史。
- 未闭合参数、重复调用和流中断都有明确策略。

### 3. `chat` 与 `stream`

`chat` 返回完整文本，控制流简单，适合作为兼容接口和降级路径。

`stream` 返回事件序列，适合实时处理。它如果只是把完整 `chat` 结果拆成字符输出，只能模拟显示效果，不能获得传输级增量能力。

当前 FakeModel 正是先得到完整结果，再逐字符输出。因此它只能验证消费者逻辑，不能验证真实 SSE 分块、截断和中途异常。

## 六、SSE 传输解析

SSE 是基于文本事件的 HTTP 流协议。解析重点是恢复协议边界，而不是直接对网络 chunk 做 JSON 解析。

正确的数据转换层次如下。

```text
Uint8Array
  -> TextDecoder
  -> 文本缓冲区
  -> 完整 SSE 事件
  -> data 字段
  -> JSON 负载
  -> ModelStreamEvent
```

### 1. 网络分块与事件分块

`reader.read` 返回的 chunk 由网络和运行时决定。一个 chunk 可以包含半个事件、一个事件或多个事件。必须使用 `buffer` 保存未闭合尾部，只处理已经形成完整边界的事件。

### 2. 文本解码

UTF-8 字符可能跨 chunk。`TextDecoder.decode` 需要使用流式模式保留未完成字节，并在底层流结束后执行最终刷新。

### 3. 结束状态

OpenAI 兼容接口通常使用结束标记表示逻辑完成。收到结束标记后应进入终止状态，后续负载不能继续计入模型输出。

### 4. 当前实现限制

- 只按两个 LF 切分，不能完整兼容 CRLF 事件边界。
- 没有合并同一事件中的多行 `data`。
- 流结束后没有刷新 decoder 和处理残余缓冲区。
- JSON 解析失败被静默忽略，无法区分心跳和协议损坏。
- 收到结束标记后没有立即终止读取。
- 迭代过程中的网络错误没有回退策略。
- 没有请求级 `AbortSignal`，无法可靠取消模型流。

修正顺序应先保证传输协议完整，再增加工具调用增量解析。传输层不可靠时，提前执行会放大重复调用和半截参数的风险。

## 七、模型输出解析与协议约束

### 1. 解析器职责

`OutputParser` 把自由文本转换为程序可执行的 `AgentAction`。

这一步建立了模型文本与程序执行面的边界。模型输出属于非可信输入，只有通过语法解析和语义校验后才能执行。

### 2. 两种输出格式

- JSON 格式优先解析，结构稳定，适合程序消费。
- ReAct 文本格式作为兼容回退，容错更强，但字段边界更模糊。

JSON 能明确区分动作名和输入对象。ReAct 回退用于处理模型没有严格遵循 JSON 协议的情况。

### 3. JSON 块提取

解析器不能只取第一个左花括号到最后一个右花括号，因为字符串内部也可能出现花括号。当前实现使用三个状态恢复平衡对象。

- `depth` 记录对象嵌套深度。
- `inString` 记录当前位置是否在字符串内部。
- `escaped` 记录字符串转义状态。

只有在字符串外部遇到右花括号并使深度回到零，才能认定对象闭合。

### 4. 语法校验与语义校验

语法校验判断文本能否转换成数据结构。语义校验判断数据结构能否成为合法动作。

语义校验至少包括：

- `action` 存在且类型正确。
- 工具动作出现在注册表中。
- `action_input` 是普通对象。
- 最终答案能提取为字符串。

当前实现对 `action_input` 直接进行类型断言。模型返回数组、数字或空值时，TypeScript 编译期不会保护运行期。必须增加运行时对象校验。

### 5. 解析失败恢复

当前策略捕获所有解析异常，统一写入格式修复提示，再次请求模型。

优点是实现简单。缺点是丢失错误类别，模型无法判断失败来自 JSON 未闭合、字段类型错误还是工具名未知。

更稳定的解析结果应区分：

- `syntax`：文本结构无法解析。
- `schema`：字段缺失或类型不符。
- `unknown_tool`：动作名不在允许集合。
- `incomplete`：流结束时结构未闭合。

错误类别决定可恢复性和修复提示内容。解析器不应把所有失败压缩成 `null`。

## 八、工具注册与执行边界

### 1. `ToolRegistry`

`ToolRegistry` 是工具定义的唯一索引，负责注册、按名称查询、列出工具和提供只读属性。

工具定义包含稳定名称、能力说明、参数 Schema、只读标记和执行函数。

注册表同时服务三个环节。

- Prompt 构建器从注册表生成工具说明。
- 输出解析器用工具名集合校验动作。
- 执行器按名称获得实际工具实现。

三处必须使用同一个注册表，否则模型看到的工具、解析器允许的工具和执行器能调用的工具会不一致。

### 2. `Executor`

`Executor` 是工具调用的统一边界，负责查找工具、执行、超时包装和异常归一化。

工具异常被转换成 `ToolResult`，不会直接让会话崩溃。模型可以把错误当作观察结果继续修复。

优点：

- 工具异常不会穿透到会话层。
- 所有工具共享一致的错误格式。
- 超时策略集中管理。

当前 `withTimeout` 只让外层 Promise 提前拒绝，没有取消底层操作。超时后的文件操作、网络请求或子进程仍可能继续执行。真正的超时需要把 `AbortSignal` 或进程终止句柄传入工具内部。

### 3. 工具结果

`ToolResult` 包含工具名、文本输出、错误标记和可选元数据。

模型历史只需要可理解的观察结果，程序轨迹应保存完整元数据。把全部信息序列化到 `output` 会增加 token 消耗，也会失去类型信息。

## 九、流式工具执行与并发安全

### 1. 并发模型

流式工具预执行的目标是在模型仍输出后续内容时，把已经完整解析的工具调用立即放入执行队列。

当前并发规则采用读写分类。

- 只读工具可以与其他只读工具并行。
- 写工具需要独占执行。
- 写工具执行期间不能启动新的读工具。
- 已运行的读工具结束后，写工具才能开始。

这是一种简化的读写锁语义。`isReadOnly` 不是展示属性，而是并发正确性的依据。

### 2. 优缺点与适用条件

优点：

- 独立读取可以降低总等待时间。
- 写操作串行化可以减少文件状态竞争。
- 工具协议扩展为多调用后无需重写执行器。

缺点：

- 只读标记错误会导致竞态或不必要的串行。
- 工具之间可能存在业务依赖，读写分类无法完整表达。
- 预执行后如果模型流最终无效，需要处理已产生的副作用。

适用条件：

- 工具调用具有稳定唯一标识。
- 参数已经完整解析并通过校验。
- 调用之间没有未表达的依赖。
- 写操作具备幂等性或可恢复机制。

### 3. 当前队列问题

`StreamingToolExecutor` 当前没有接入主链路，因此不会实际执行预提交工具。

队列实现本身还有推进风险。写工具运行时，如果后续任务因独占规则无法启动，`processQueue` 会退出。工具完成回调没有重新触发队列处理，后续任务可能永久停留在 `queued`，而 `collect` 会持续等待。

修复原则：

- 工具完成后的 `finally` 必须再次调度队列。
- 同一时间只允许一个调度器修改队列状态。
- `collect` 基于通知或 Promise 完成信号，不使用固定间隔轮询。
- 失败任务也必须进入终态并唤醒等待者。
- 返回结果按提交顺序排列，执行顺序可以不同。

## 十、Prompt 构建与上下文预算

### 1. Prompt 组成

`PromptBuilder` 把稳定规则和动态状态组装成模型消息。

内容包括：

- Agent 身份与目标。
- 可用工具及参数 Schema。
- 输出协议。
- 行为规则。
- 当前子任务。
- 项目规则。
- 已完成任务摘要。
- 工作记忆。
- 截断后的对话历史。

Prompt 是运行时工具能力、项目约束和任务状态的统一视图。任何部分与真实运行状态不一致，都会导致模型产生不可执行决策。

### 2. 稳定信息与动态信息

稳定信息包括身份、输出协议、工具定义和项目规则。动态信息包括当前任务、已完成摘要、工作记忆和消息历史。

合理顺序是先放稳定信息，再放动态信息。这有利于模型组织注意力，也有利于服务端 Prompt 缓存。

当前实现把当前子任务放在项目规则之前，与稳定到动态的顺序不完全一致。更合理的顺序如下。

```text
身份与固定规则
  -> 工具定义
  -> 项目规则
  -> 工作记忆
  -> 当前任务与完成摘要
  -> 对话历史
```

### 3. token 估算

当前实现使用启发式估算。

- CJK 字符按一个 token 估算。
- 其他字符按四个字符约一个 token 估算。
- 每条消息增加固定协议开销。

优点是无模型依赖、计算快。缺点是不同模型的分词器差异较大，代码、JSON 和混合语言文本的误差明显。

它适合本地预算预警和粗粒度截断，不适合精确成本统计或临界上下文控制。

### 4. 历史截断

当前截断逻辑保留首个 assistant 消息之前的前缀，再把后续消息按 assistant 开头分组为完整轮次，从最早轮次开始删除。

核心优点是按轮删除，避免只删 assistant 或只删 tool 导致对话结构断裂。

当前限制：

- 初始用户任务始终保留，即使已经超过预算。
- 只删除历史，不做摘要和大工具结果落盘。
- system prompt 本身超预算时没有降级策略。
- token 估算误差可能导致请求仍然超限。

Phase 1 只提供最小预算保护。多级压缩、结果落盘和精确 usage 锚点属于后续阶段。

## 十一、分层配置

### 1. 配置优先级

分层配置让默认值、用户偏好、项目约束和本次运行覆盖可以同时存在，并通过固定优先级得到唯一结果。

```text
builtin < user < project < local
```

- `builtin` 提供程序默认值，保证无配置文件时仍可运行。
- `user` 位于用户主目录，对所有项目生效。
- `project` 位于项目目录，表达仓库级要求。
- `local` 来自环境变量和命令行，只影响当前环境或运行。

低优先级先合并，高优先级后覆盖。嵌套对象需要深度合并，不能整体替换。

### 2. 配置补丁

除 `builtin` 外，其他层保存的应该是补丁，不是完整配置。只有显式设置的字段才能覆盖低优先级结果。

如果高优先级层自动填充默认值，它会把低优先级的有效配置覆盖掉，分层机制只剩形式。

### 3. 当前实现问题

`loadLayeredConfig` 把 `loadConfig` 的返回值作为 `local` 层。`loadConfig` 会为所有字段填入默认值，因此环境变量没有设置时，`local` 层仍会用默认值覆盖 `user` 和 `project`。

结果是声明的优先级存在，但用户级和项目级数值在多数情况下无法生效。

根本修复方式：

- `builtinConfig` 生成完整默认值。
- 环境变量解析器只返回实际存在的字段。
- CLI 解析器只返回显式传入的字段。
- `.env`、进程环境和 CLI 拆成独立层并明确优先级。
- 合并完成后执行完整配置校验。

### 4. TOML 子集解析

当前解析器支持注释、扁平键值、单层 section、字符串、数字和布尔值。

优点是依赖少，足以覆盖当前配置。缺点是它不是完整 TOML，不支持数组、日期、多行字符串、完整转义和复杂嵌套。

实现要点：

- 注释符只在字符串外生效。
- section 改变后续键值的写入对象。
- 解析结果先保持通用对象，再由 `tomlToConfig` 做字段映射和类型筛选。
- 未知字段应产生诊断，不能长期静默忽略拼写错误。
- 非法值应在启动期失败，不能带着部分错误配置运行。

### 5. 运行时校验

类型断言不能代替运行时校验。外部配置至少需要检查：

- 步数和 token 上限是正整数。
- 超时时间处于合理范围。
- 工作目录存在并可访问。
- 模型地址是合法 URL。
- 真实模型模式下 API Key 满足要求。
- 模型嵌套字段合并后保持完整。

当前 `mergeLayers` 最后直接断言为 `AgentConfig`，可能把缺失字段带入运行期。应使用显式校验函数把未知对象转换成完整配置。

## 十二、`AGENTS.md` 与 `CLAUDE.md` 注入

### 1. 作用与边界

项目规则文件用于把仓库约束注入 system prompt，使模型在每轮都能看到项目语言、目录规范、验证命令和操作限制。

它与其他上下文的区别：

- 项目规则来自文件，是仓库维护者声明的约束。
- 工作记忆来自运行过程，是当前会话的临时状态。
- 对话历史来自模型交互，是推理所需上下文。

三者来源、可信度和生命周期不同，必须分别组织。

### 2. 向上发现

发现过程从工作目录向父目录逐级查找，遇到项目根标记后停止。子目录任务因此可以继承上层规则。

项目根标记的作用是限制发现范围，防止继续读取无关父目录，不只是判断项目类型。

### 3. 合并顺序与作用域

父目录规则应先注入，子目录规则后注入。后出现的内容代表更具体的作用域，适合覆盖上层通用约束。

同一目录同时存在两类规则文件时，需要规定固定顺序并明确优先关系。当前实现依赖循环和数组插入顺序，没有显式优先级模型。

### 4. 字节预算

规则文件使用字节预算，优点是无需模型分词器，缺点是与实际 token 占用不一致。

当前实现有两个关键问题。

- 先读取父级内容，预算不足时可能截断更具体的子目录规则。
- 使用字符串长度切片模拟字节截断，UTF-8 多字节字符会让实际字节数超过预算，也可能破坏字符边界。

更稳妥的策略：

- 先计算全部候选文件和作用域。
- 优先完整保留最近目录规则。
- 使用 `Buffer` 按字节边界截断后安全解码。
- 在 Prompt 总预算层再次计算 token 占用。
- 截断信息进入诊断事件，不能只打印 warning。

### 5. 根边界

规则发现依赖项目根标记。工作目录没有根标记时，查找会继续向文件系统根目录推进，可能加载仓库外规则。

启动时应明确计算项目根，或者允许配置自定义根标记和停止目录。

## 十三、任务规划与调度

### 1. 任务规划

`TaskPlanner` 支持两种模式。

- 关闭 LLM 规划时，整个用户请求作为单个任务。
- 开启 LLM 规划时，先请求模型生成任务数组，解析失败则退回单任务。

规划阶段与执行阶段使用同一个模型客户端，但协议不同。规划响应只接受数组结构，执行响应接受动作结构，因此两者需要独立解析和错误诊断。

优点是复杂请求可以形成阶段边界。缺点是增加模型调用延迟，错误拆分还会让后续任务建立在错误前提上。

适用条件：

- 子任务之间有清晰顺序。
- 每个子任务可以独立判断完成。
- 已完成结果能够压缩为后续任务需要的摘要。

### 2. 当前调度器

`TaskScheduler` 使用后进先出栈，通过逆序压入保持规划顺序。它只管理 pending 到 in_progress 的转移，没有依赖判断、失败重试和优先级。

`Task` 类型已经包含 `dependsOn`，调度器没有使用它。类型表达了未来能力，运行逻辑尚未实现依赖图调度。

### 3. 多任务结果

每个子任务返回 final answer 后会被标记完成，并把摘要注入后续 Prompt。所有任务结束时，`AgentSession` 返回最后一个子任务的答案，而不是聚合后的整体结果。

这只适合最后一个任务负责总结的规划方式。稳定方案是在队列结束后增加结果汇总阶段，或者由规划器保证最后任务承担整体收敛。

## 十四、错误分层与恢复原则

Agent 错误必须按发生层次处理，不能统一转换成一个失败字符串。

### 1. 配置错误

发生在启动阶段。字段非法、文件不可读、工作目录无效时应尽早失败。配置错误不进入模型重试。

### 2. 传输错误

发生在 HTTP 请求、SSE 读取和连接中断阶段。请求尚未产生有效输出时可以退避重试或降级为非流式。已经产生部分输出后，直接重试可能导致重复动作，需要先判断响应能否安全重放。

### 3. 协议解析错误

发生在模型文本到动作的转换阶段。可以通过结构化修复提示让模型重试，但需要限制次数并保存错误类别。

### 4. 工具校验错误

发生在工具名、参数类型和路径约束检查阶段。错误应在副作用发生前返回。

### 5. 工具运行错误

发生在文件、终端和搜索操作内部。可恢复错误作为观察结果写回模型，不可恢复错误终止当前任务。

### 6. 会话控制错误

包括达到预算、任务队列异常和恢复次数耗尽。它们应产生准确终止原因。

当前解析失败退出后仍会统一发出 `max_turns_reached`，最终文本也同时表示达到最大步数或队列为空。不同终止原因被合并，降低了可观测性。应使用明确终态区分完成、预算耗尽、解析失败、规划为空和内部错误。

## 十五、TypeScript 实现原则

### 1. 判别联合

`AgentAction`、`AgentEvent` 和 `ModelStreamEvent` 都适合使用判别联合。每个分支通过固定 `type` 字段区分，`switch` 可以获得类型收窄。

优点是新增状态时编译器能帮助检查遗漏分支。要发挥这一能力，需要使用穷尽检查，不能依赖默认分支吞掉未知事件。

### 2. `unknown` 优先

模型输出、TOML 内容和工具输入都来自外部，初始类型应是 `unknown`。只有通过运行时校验后才能转换成领域类型。

`as Record<string, unknown>` 只改变编译器判断，不改变真实数据。strict 模式能检查静态代码，不能自动验证运行时 JSON。

### 3. 可变状态集中

每种可变状态应有唯一维护者。

- `TaskScheduler` 维护任务出队顺序。
- `AgentSession` 维护会话级状态。
- `runTurn` 维护单轮临时状态。
- `StreamingToolExecutor` 维护工具队列状态。

多个组件同时修改同一状态时，必须增加所有权规则和同步机制。

### 4. 异步资源清理

模型 reader、终端子进程、超时计时器和持久 shell 都属于异步资源。资源获取后应使用 `try` 和 `finally` 保证所有退出路径都能清理。

当前入口在 `finally` 中关闭 shell，方向正确。模型流 reader 和工具超时还需要同样的清理语义。

## 十八、最终结论

Phase 1 的核心成果是建立控制面，不是增加更多工具。

- 双层循环把会话策略与单轮执行分离，为恢复机制提供稳定插入点。
- 事件流把运行核心与展示层分离，但事件协议必须有稳定标识和完整终态。
- 流式模型接口只有在能解析结构化工具调用时，才能转化为工具预执行能力。
- 输出解析器是非可信模型文本进入执行面的安全边界，必须同时做语法和语义校验。
- 工具注册表保证 Prompt、解析和执行使用同一能力集合。
- 并发安全依赖正确的只读分类、队列推进和副作用控制。
- Prompt 构建决定模型看到的真实状态，上下文预算必须保持消息结构完整。
- 分层配置的关键不是读取多个文件，而是只有显式值能够覆盖低优先级层。
- 项目规则注入需要明确作用域、顺序、根边界和预算策略。
- 类型定义只代表设计意图，只有接入实际控制流后才算能力落地。

掌握这一阶段后，应能从入口沿数据流定位任何一次模型调用、动作解析、工具执行和配置覆盖的来源，并能判断某个类型或类已经生效，还是只完成了结构预留。
